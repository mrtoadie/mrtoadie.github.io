Hardware Physical Layer

Raspberry Pi 4 · USB-SSDs · SD-Karten · Netzwerktopologie
kubectl get nodes -o wide + physical specs
Node Board RAM Storage Rolle Bemerkungen
winterfell Raspberry Pi 4 8 GB USB-SSD (XFS) control-plane Root auf USB etcd auf NVMe
worker01 Raspberry Pi 4 1 GB Samsung EVO SD worker Pod-Limits Thermal Throttling
worker02 Raspberry Pi 4 1 GB Samsung EVO SD worker NFS Client
worker03 Raspberry Pi 4 2 GB Samsung EVO SD worker Heißer Arbeiter
Warum USB-SSD statt SD-Karte? Die SD-Karten auf winterfell sind zweimal innerhalb von sechs Monaten gestorben — einmal korruptes etcd, einmal bootblock defekt. Seitdem läuft rootfs und /var/lib/k3s auf einem Sandisk Extreme Plus USB-SSD via Realtek RTL9210-Adapter. Der Adapter braucht Kernel 6.2+, funktioniert aber nicht stabil unter allen Raspberry Pi OS-Versionen.
cgroup-Limits auf den 1-GB-Pis: worker01/02 haben `--kubelet-arg=max-pods=20` und `--kubelet-arg=eviction-hard=memory.available<100Mi`. Ohne diese Limits kippen sie regelmäßig in OOM-Kill-Schleifen, sobald Buchlore oder Grafana etwas mehr RAM ziehen.

Gesamtverbrauch im Idle: ~35W (alle 4 Nodes + Switch + NAS). Spitzenlast bei Velero-Backup oder大规模 Deployment: bis zu 65W. Strompreis (DE, 2026): ca. €0,35/kWh → Jahreskosten ~€35–45 je nach Auslastung.

peripherals · switches · power delivery
Netzwerk: TP-Link TL-SG105 (5-Port Gigabit Unmanaged)

USV: PiZero UPS HAT auf winterfell, keine automatische Shutdown-Logik

Cooling: Argon ONE M.2 Case auf winterfell (aktiv gekühlt), passive Heatsinks auf workers

NFS-Server: Synology DS220j (nicht im Cluster, separat an FRITZ!Box)
