Incident History — echte Vorfälle letzte 12 Monate
high
SD-Karte corruptions auf winterfell
Januar 2026 · Dauer: 4 Stunden · Impact: control-plane offline

etcd meldete `database error: snapshot corrupted`. Logs zeigten I/O-Fehler auf `/dev/mmcblk0`. Node konnte nicht neu starten, etcd-Cluster fiel auf 1 Mitglied (Quorum verloren).

  1. Neues Image von Raspberry Pi OS Lite auf SD-Karte gebrannt
  2. k3s-Token von backup-node manuell kopiert
  3. Node wieder mit Cluster verbunden, etcd-Replizierung initiiert
  4. Nach Incident: Rootfs auf USB-SSD migriert, etcd auf separates Volume ausgelagert
high
Docker Daemon durch TCP-Listener lahmgelegt
Februar 2026 · Dauer: 2 Stunden · Impact: keine Container-Starts möglich

Versucht, Docker über TCP zu aktivieren (`-H tcp://0.0.0.0:2375`). Danach `systemctl start docker` fehlgeschlagen mit `Failed to start Docker Application Container Engine`. Logs zeigten Socket-Conflict mit existiersnder Unix-Socket.

  1. Docker Service gestoppt
  2. `/etc/docker/daemon.json` auf Leerzeichen überprüft, TCP-Entry entfernt
  3. Service neu gestartet, Funktionstest mit `docker ps`
  4. Später: Nur Unix-Socket, SSH-Tunnel für Remote-Zugriff
medium
Pi Zero unter Blocky instabil
März 2026 · Dauer: 1 Stunde · Impact: DNS-Auflösung intermitierend fehlgeschlagen

Blocky (DNS Resolver) lief auf Raspberry Pi Zero 2W, 100% CPU-Last nach 3 Tagen Uptime. Gerät wurde unresponsive, musste hart neu gestartet werden.

  1. Blocky auf Desktop (Docker) migriert, Pi Zero nur noch Dynacat
  2. Pi Zero auf statische IP mit manueller DNS-Einträge in Dynacat konfiguriert
  3. Alternative evaluiert: Unbound statt Blocky, weniger Ressourcen-intensiv
medium
Node Rejoin nach k3s-Update — Token Mismatch
April 2026 · Dauer: 30 Minuten · Impact: worker01 NotReady

k3s-Update auf control-plane durchgeführt. Nach Neustart meldete worker01 `token mismatch`. Agent konnte sich nicht authentifizieren, Pod-Scheduling unterbrochen.

  1. Token von `/var/lib/rancher/k3s/server/node-token` auf control-plane ausgelesen
  2. Auf worker01 in `/etc/rancher/k3s/config.yaml` eingefügt
  3. k3s-agent neu gestartet, Node wieder im Cluster sichtbar
  4. Lösung: Automatisiertes Backup des Tokens auf externer Maschine
low
OpenVPN Replay Detection Error
Mai 2026 · Dauer: 15 Minuten · Impact: Tunnel nicht aufgebaut

`read UDPv4 [EAGAIN]: Resource temporarily unavailable (code=11)` während Tunnel-Etablierung. Replay Detection war zu aggressiv eingestellt.

  1. openvpn.conf: `replay-window 64 15` statt Standard-Werte
  2. Tunnel neu initialisiert, Verbindung stabil
