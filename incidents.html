SD-Karte Corruptions auf winterfell
Januar 2026 · Dauer: 4 Stunden · Impact: control-plane offline

etcd meldete `database error: snapshot corrupted`. Logs zeigten I/O-Fehler auf `/dev/mmcblk0`. Node konnte nicht neu starten, etcd-Cluster fiel auf 1 Mitglied (Quorum verloren).

Aktionen:
  1. Neues Image von Raspberry Pi OS Lite auf SD-Karte gebrannt
  2. k3s-Token von backup-node manuell kopiert
  3. Node wieder mit Cluster verbunden, etcd-Replizierung initiiert
  4. Nach Incident: Rootfs auf USB-SSD migriert, etcd auf separates Volume ausgelagert
Lesson Learned:

etcd auf SD-Karte ist riskant bei Rolling Updates. USB-SSD + separater etcd-Partition als Minimum. Backup des Tokens auf externe Maschine.

Docker Daemon durch TCP-Listener lahmgelegt
Februar 2026 · Dauer: 2 Stunden · Impact: keine Container-Starts möglich

Versucht, Docker über TCP zu aktivieren (`-H tcp://0.0.0.0:2375`). Danach `systemctl start docker` fehlgeschlagen mit `Failed to start Docker Application Container Engine`. Logs zeigten Socket-Conflict mit existierender Unix-Socket.

Aktionen:
  1. Docker Service gestoppt
  2. `/etc/docker/daemon.json` geprüft, TCP-Einträge entfernt
  3. Service neu gestartet, Funktionstest mit `docker ps`
  4. Entscheidung: Nur Unix-Socket, SSH-Tunnel für Remote-Zugriff
Lesson Learned:

Docker TCP-Listener ohne TLS = Security Risk. SSH-Tunnel ist sicherer als offene Ports. Changes immer erst in Staging testen.

Pi Zero unter Blocky instabil
März 2026 · Dauer: 1 Stunde · Impact: DNS-Auflösung intermittierend fehlgeschlagen

Blocky (DNS Resolver) lief auf Raspberry Pi Zero 2W, 100% CPU-Last nach 3 Tagen Uptime. Gerät wurde unresponsive, musste hart neu gestartet werden.

Aktionen:
  1. Blocky auf Desktop (Docker) migriert, Pi Zero nur noch Dynacat
  2. Pi Zero auf statische IP mit manueller DNS-Einträge in Dynacat konfiguriert
  3. Alternative evaluiert: Unbound statt Blocky, weniger ressourcenintensiv
Lesson Learned:

Pi Zero 2W ist极限 für 1 Container. Blocky benötigt mehr RAM als verfügbar bei langer Laufzeit. Hardware Limits dokumentieren.

Medium
Velero Metrics nicht in Prometheus sichtbar
Juni 2026 · Dauer: 45 Minuten · Impact: kein Monitoring der Backups

ServiceMonitor für Velero erstellt, aber Metriken erschienen nicht in Prometheus. Logs zeigten `target scrape failed` — Label-Mismatch zwischen ServiceMonitor und Service (`app.kubernetes.io/instance` vs. `release`).

Aktionen:
  1. ServiceMonitor-Labels angepasst (helm chart release name = `monitoring`)
  2. Prometheus Reload getriggert durch Annotation
  3. Velero-Endpoints in Prometheus sichtbar, Dashboards aktualisiert
  4. Template für ServiceMonitor erstellt, um Fehler zu vermeiden
Lesson Learned:

Helm Release-Namen sind entscheidend für ServiceMonitors. Vor Deployment Labels mit `kubectl get svc -o yaml` prüfen. Dokumentieren, welcher Helm Release Name verwendet wird.

GitGuardian Alert — Kubernetes JWT im öffentlichen Repo
Juli 2026 · Dauer: 2 Stunden · Impact: Sicherheitsrisiko, Repository geleakt

GitGuardian meldete exponiertes JWT-Token in öffentlichem GitHub-Repository. Das Token hatte Zugriff auf k3s API Server mit cluster-admin-Rechten. Repository war kurzzeitig öffentlich.

Aktionen:
  1. Repository sofort privat gestellt
  2. JWT-Token invalidiert, neues ServiceAccount-Token erstellt
  3. GitGuardian-Scan in CI/CD Pipeline integriert
  4. .gitignore aktualisiert, um kubeconfig und Secrets zu schützen
  5. Commit-History mit git-filter-repo bereinigt
Lesson Learned:

Secret Scanning ist kein Feature, sondern Mandatory. Pre-commit Hooks mit gitleaks/gitguardian-cli. Keine Secrets in History – git-secrets oder BFG Repo-Cleaner bei Leaks.
