etcd Corruption durch SD-Karte — Migration auf USB-SSD
Januar 2026 · Dauer: 4 Stunden · Impact: control-plane offline, Quorum verloren

Nach mehreren Wochen Betrieb meldete etcd auf winterfell plötzlich `database error: snapshot corrupted`. Die Logs auf `/var/log/syslog` zeigten wiederholte I/O-Fehler auf der SD-Karte (`mmcblk0: error -110`). Der Control-Plane-Node startete nicht mehr — der k3s-Service konnte die etcd-Datenbank nicht öffnen.

Ohne winterfell blieb nur noch ein Mitglied im etcd-Cluster (1 von 3). Das Quorum ging verloren, alle Pods blieben auf dem Status quo — kein Scheduling, keine Neustarts. Per `kubectl get nodes` war winterfell `Unknown`, worker01-03 funktionierten technisch, konnten aber keine Entscheidungen vom Controller empfangen.

Aktionen:
  1. Karte ausgelesen, `journalctl -u k3s` zeigte korrupte WAL-Segmente
  2. Vom Backup-Node das letzte `etcd-snapshot` wiederhergestellt
  3. Schneller Workaround: k3s neu installieren, Token vom Control-Plane kopiert
  4. Node wieder in den Cluster integriert, etcd-Replikation lief an
  5. Nachbearbeitung: Rootfs auf USB-SSD migriert, etcd-Datenverzeichnis auf separate Partition ausgelagert
  6. NFS-Storage-Provisioner getestet für persistente Volumes aller Services (Booklore, Forgejo, Vaultwarden, etc.)
Lesson Learned:

SD-Karten sind für sequentiellen Lesezugriff gebaut, nicht für permanente Schreibarbeit. etcd schreibt kontinuierlich Snapshots, WAL-Einträge und Transaktionslogs — genau das Muster, das SD-Karten langfristig zerstört. Der Ausfall war absehbar, nur der Zeitpunkt war Zufall.

Best Practice: Für jeden Stateful Service mit kritischen Daten (etcd, PostgreSQL, Redis persistent) mindestens eine USB-SSD oder NVMe verwenden. SD-Karte maximal für das Bootstrap-Image, nicht für persistente Daten.

Infrastructure as Code: Alle Services nutzen NFS Persistent Volumes über den nfs-subdir-external-provisioner. Bei einem kompletten Node-Ausfall können die Daten einfach auf einer neuen Installation wieder eingebunden werden — die Anwendungskonfiguration bleibt im Git-Repo, die Daten auf dem NFS.

k3s Update-Problematik — Token Mismatch und Agent Reconnect
April 2026 · Dauer: 30 Minuten · Impact: worker01 NotReady, Pod-Scheduling unterbrochen

k3s wurde auf winterfell (Control-Plane) auf die nächste Minor-Version aktualisiert (`v1.36.3+k3s1`). Der Agent auf worker01 konnte sich anschließend nicht mehr authentifizieren und meldete im Cluster `token mismatch`. Die Logs auf worker01 zeigten `failed to register node: unauthorized`.

k3s wechselt bei einem Major/Minor-Update teilweise die internen Protokolle zwischen Server und Agent. Das node-token, das für die Authentifizierung verwendet wird, wird bei einem Control-Plane-Upgrade neu generiert. Worker-Nodes wissen davon nichts und versuchen weiter mit dem alten Token zu kommunizieren.

Aktionen:
  1. Token vom Control-Plane ausgelesen: cat /var/lib/rancher/k3s/server/node-token
  2. Token auf worker01 in /etc/rancher/k3s/config.yaml eingefügt
  3. k3s-agent neu gestartet, Node wieder als Ready sichtbar
  4. Automatisiertes Backup des Tokens auf externer Maschine eingerichtet
Lesson Learned:

Rolling Updates sind riskant bei Agent-basierten Clustern. k3s dokumentiert zwar Kompatibilität innerhalb einer Minor-Version, aber bei Minor-Upgrades kann sich die API oder Authentication ändern. Die Regel: immer erst auf einem Worker testen, dann den Control-Plane updaten.

Token-Management: Das node-token ist wie ein Passwort. Es sollte regelmäßig rotiert werden (Security), aber auch gesichert sein (Disaster Recovery). Ein automatisches Backup des Tokens vor jedem Update verhindert, dass man nach einem Upgrade im Dunkeln tastet.

Dokumentation: Ein kurzes Runbook für Node-Recovery sollte in der Dokumentation liegen: welche Dateien wo gespeichert, welcher Pfad für das Token, wie man einen Node neu joint. Die Zeiten von "googlen, wenn der Node ausfällt" sind vorbei — spätestens beim zweiten Incident merkt man den Wert dokumentierter Abläufe.

SD-Karte Corruptions auf winterfell
Januar 2026 · Dauer: 4 Stunden · Impact: control-plane offline

etcd meldete `database error: snapshot corrupted`. Logs zeigten I/O-Fehler auf `/dev/mmcblk0`. Node konnte nicht neu starten, etcd-Cluster fiel auf 1 Mitglied (Quorum verloren).

Aktionen:
  1. Neues Image von Raspberry Pi OS Lite auf SD-Karte gebrannt
  2. k3s-Token von backup-node manuell kopiert
  3. Node wieder mit Cluster verbunden, etcd-Replizierung initiiert
  4. Nach Incident: Rootfs auf USB-SSD migriert, etcd auf separates Volume ausgelagert
Lesson Learned:

etcd auf SD-Karte ist riskant bei Rolling Updates. USB-SSD + separater etcd-Partition als Minimum. Backup des Tokens auf externe Maschine.

Docker Daemon durch TCP-Listener lahmgelegt
Februar 2026 · Dauer: 2 Stunden · Impact: keine Container-Starts möglich

Versucht, Docker über TCP zu aktivieren (`-H tcp://0.0.0.0:2375`). Danach `systemctl start docker` fehlgeschlagen mit `Failed to start Docker Application Container Engine`. Logs zeigten Socket-Conflict mit existierender Unix-Socket.

Aktionen:
  1. Docker Service gestoppt
  2. `/etc/docker/daemon.json` geprüft, TCP-Einträge entfernt
  3. Service neu gestartet, Funktionstest mit `docker ps`
  4. Entscheidung: Nur Unix-Socket, SSH-Tunnel für Remote-Zugriff
Lesson Learned:

Docker TCP-Listener ohne TLS = Security Risk. SSH-Tunnel ist sicherer als offene Ports. Changes immer erst in Staging testen.

Medium
Pi Zero :: Blocky instabil
Oktober 2026 · Impact: DNS-Auflösung intermittierend fehlgeschlagen

Blocky (DNS Resolver) lief auf Raspberry Pi Zero 2W, 100% CPU-Last, hohe wärme entwicklung. Gerät wurde unresponsive, musste hart neu gestartet werden.

Aktionen:
  1. Alternative evaluiert: Unbound statt Blocky, weniger ressourcenintensiv
Lesson Learned:

Blocky läuft als Container nicht zuverlässig auf einem Pi Zero 2W. Unbound ist eine sehr brauchbare und stabile Alternative.

Velero Metrics nicht in Prometheus sichtbar
Juni 2026 · Dauer: 45 Minuten · Impact: kein Monitoring der Backups

ServiceMonitor für Velero erstellt, aber Metriken erschienen nicht in Prometheus. Logs zeigten `target scrape failed` — Label-Mismatch zwischen ServiceMonitor und Service (`app.kubernetes.io/instance` vs. `release`).

Aktionen:
  1. ServiceMonitor-Labels angepasst (helm chart release name = `monitoring`)
  2. Prometheus Reload getriggert durch Annotation
  3. Velero-Endpoints in Prometheus sichtbar, Dashboards aktualisiert
  4. Template für ServiceMonitor erstellt, um Fehler zu vermeiden
Lesson Learned:

Helm Release-Namen sind entscheidend für ServiceMonitors. Vor Deployment Labels mit `kubectl get svc -o yaml` prüfen. Dokumentieren, welcher Helm Release Name verwendet wird.
